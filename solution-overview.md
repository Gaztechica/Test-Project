# Архитектурный обзор решения (Solution Overview)

## Схема архитектуры фреймворка
Ниже представлена архитектура фреймворка автоматизации, демонстрирующая разделение слоев логики, конфигурации и тестовых сценариев:

```mermaid
graph TD
    subgraph Слой Сценариев (BDD / Тесты)
        Feature[Gherkin .feature файлы] --> Steps[Слой Шагов: ApiAuthSteps / LoginSteps]
        JunitTests[JUnit 5 Параметризованные тесты] --> Steps
    end

    subgraph Слой Бизнес-Логики и Абстракций
        Steps --> PO[Page Object: LoginPage]
        Steps --> Client[API Client: ApiClient]
    end

    subgraph Инфраструктурный слой
        PO --> Selenium[Selenium / WebDriver]
        Client --> RestAssured[Rest Assured]
        InitSQL[init.sql] --> DB[(PostgreSQL)]
    end

    subgraph Конфигурация и Отчетность
        Config[ConfigReader] --> Steps
        Properties[allure / cucumber.properties] --> Allure[Allure Reports]
    end
```

## Паттерны проектирования

### 1. Page Object Model (POM)
* **Назначение:** Разделение логики элементов интерфейса и непосредственного выполнения проверок.
* **Реализация:** Класс `LoginPage` инкапсулирует в себе локаторы страниц (кнопки, текстовые поля авторизации) веб-ресурса (например, Saucedemo). Шаги сценариев взаимодействуют со страницей исключительно через высокоуровневые методы класса `LoginPage`, что защищает тесты от изменений верстки.

### 2. Слой Steps (Шаги Cucumber / BDD)
* **Назначение:** Перевод текстовых инструкций Gherkin (из файлов `api_auth.feature` и `ui_tests.feature`) в исполняемый Java-код.
* **Реализация:** Классы `ApiAuthSteps` и `LoginSteps` связывают аннотации `@Given`, `@When`, `@Then` с вызовами соответствующих API-клиентов или Page Object-страниц.

## Стратегия работы с БД и очередями

### 1. Работа с Базой Данных (PostgreSQL)
* **Инициализация:** Для изоляции состояния тестов и подготовки тестовых данных используется скрипт `init.sql` (`src/test/resources/init.sql`).
* **Жизненный цикл:** Скрипт автоматически выполняется при запуске контейнера базы данных через `docker-compose.yml`, наполняя таблицы базовыми пользователями и параметрами аутентификации перед стартом прогона.
* **Очистка данных:** Осуществляется через транзакционные механизмы или хуки очистки (`Hooks.java`) после завершения сценариев.

### 2. Работа с очередями сообщений (Перспектива)
* Архитектура фреймворка предусматривает расширение для тестирования асинхронного взаимодействия. Модули очередей планируется интегрировать на уровне `ApiClient` / брокеров сообщений для валидации сквозных событий (микросервисных эвентов).
