# Сравнение Selenium WebDriver и Selenide

В данном анализе сравниваются два подхода к автоматизации тестирования на примере базового сценария 
авторизации на тестовом стенде test.sauceDemoSelenium.

## Сравнительная таблица

| Критерий | Чистый Selenium WebDriver | Selenide |
| :--- | :--- | :--- |
| **Объем бойлерплейта** | **Высокий**. <br/>Требуется вручную прописывать конфигурацию драйвера (`ChromeDriver`), управлять его сессией (`driver.quit()`), а также для каждого нестабильного шага создавать инстанс `WebDriverWait` с указанием `ExpectedConditions`. | **Минимальный**. <br/>Открытие браузера, управление сессией, закрытие окон и создание скриншотов при падении происходят под капотом автоматически. Код сфокусирован только на бизнес-логике шагов. |
| **Читаемость ассертов** | **Низкая / Средняя**. <br/>Ассерты разделены на техническую проверку состояния элемента и стандартные утверждения тестового фреймворка (например, `assertTrue(element.isDisplayed())`). Сообщения об ошибках малоинформативны без кастомного текста. | **Высокая**. <br/>Используется человекочитаемый DSL-стиль (`element.shouldBe(visible)`). В случае падения Selenide выдает подробный отчет: что искали, сколько ждали, состояние DOM и скриншот. |
| **Решение проблемы "протухания" DOM (StaleElementReferenceException)** | **Ручное**. <br/>Если страница обновляется по AJAX/JS, старая ссылка на элемент в памяти "протухает". Тестировщик вынужден вручную перехватывать исключение, делать повторный поиск `findElement` или оборачивать вызовы в `wait.until(...)`. | **Автоматическое (Умное)**. <br/>Selenide решает проблему динамического DOM с помощью концепции **"ленивого поиска" (Lazy Evaluation)**. Элемент не ищется в момент объявления, а обертка `SelenideElement` осуществляет повторный поиск элемента на странице прямо в момент совершения действия (`click`, `setValue`, `shouldBe`), если старый элемент исчез. |

## Как Selenide решает проблему динамического (протухающего) DOM

Главное архитектурное отличие Selenide от Selenium в работе с нестабильным DOM-деревом 
(AJAX, React/Vue/Angular подгрузки) заключается в том, что Selenide **автоматически перезапрашивает 
элемент из DOM**, если тот изменился или временно пропал.

Когда вы вызываете метод (например, `$("#login-button").click()`), Selenide запускает цикл ожидания 
(по умолчанию 4 секунды). Если в этот момент браузер перерисовывает страницу и падает `StaleElementReferenceException`, 
Selenide не роняет тест. Он мгновенно находит элемент на странице заново по селектору и повторяет действие. 
Тестировщику больше не нужно писать громоздкие циклы или расставлять `ExpectedConditions` перед каждым кликом.
